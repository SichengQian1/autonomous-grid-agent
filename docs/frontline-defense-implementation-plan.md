## 1. 交付目标与范围

根据敌人的主要来路安排防御，把有限的石头、金币和角色行动优先花在有效防线上：

- 正面优先建墙；敌群拥挤、向两侧分流时，靠近正面的侧翼也应视压力提前补墙，优先维护实际承受攻击的位置。
- 火箭优先放后方，直线武器优先放能覆盖正面且有射击通道的侧后方。
- 塔位、操控位、墙段和出入口联合规划，不能各自排序后拼在一起。
- 比较修复、升级、补墙的收益，避免先铺满无用墙、再平均升级。
- 保留现有策略作为对照，新策略由独立配置开启。

本次交付包括代码、配置、合成测试、只读诊断和文档。不得把“有防御布局”写成“已经提高胜率”。

## 2. 规则与证据边界

### 2.1 本次采用的依据

| 信息 | 依据与实现方式 |
| --- | --- |
| 基地在左上时，敌人从右上来；基地在右下时，敌人从左下来 | 用户的运行观察，作为初始水平来敌方向的先验，不扩展为所有地图永久成立的规则 |
| 武器位于距完整基地占地 1 格的蓝圈，墙位于 2 格黄圈 | 用户确认；复用现有 `build_cells()` 与验证层 |
| 八方向移动、切比雪夫距离，允许相邻障碍间的对角穿行 | 当前规则和实现；布局连通性检查必须保持一致 |
| 建墙需要工人、白天、石头和相邻位置 | 当前协议验证约束；不绕开验证器 |
| 使用墙升级券、修复包需要到目标附近 | 当前道具验证约束；可维护性要纳入选址 |
| 升级恢复建筑满血 | 已读规则支持；用于计算升级的恢复收益 |
| 商店价格、单位属性可能变化 | 优先运行时字段，缺失时使用有来源的集中配置或保守跳过 |
| 机器人会攻击阻挡其移动的单位 | 已读规则支持；不足以推导精确寻路、仇恨和目标选择顺序 |
| 墙和基地不阻挡武器弹道 | 用户补充确认；基地、已有墙和计划墙均不计入弹道障碍，仍阻挡移动 |
| 火箭不受沿途障碍阻挡 | 已读规则支持；射程、冷却和操控限制仍需检查 |

只使用规则的中性技术表述，不向文档、注释或测试复制官方原文和内部链接。

### 2.2 必须保留的不确定性

1. **前墙不是已验证的伤害屏障。** 机器人有射程；墙在基地外两格，不代表它一定先打墙，也不代表墙能阻挡攻击射线。布局和危险区域计算不能假定“墙后就安全”。
2. **其他武器工事与直线武器的相互作用尚待平台验证；墙和基地已确认不阻挡武器弹道。** 保留 `projectile_building_blocking`，默认沿用当前保守值。不能为了让后方塔有输出，直接把它改为 `false`。
3. 出生区域不等于整夜唯一来路。用户观察到敌人较多时会相互拥挤，部分敌人分流到侧翼，因此前排两端附近也可能成为受压位置。采用这一观察指导风险评估，但不据此假定精确的拥挤、避让和寻路算法；绕行和额外机器人同样可能造成侧翼压力。
4. 血量下降只能说明单位受损，不能唯一确定攻击者；单位消失也不能无条件认定死亡。
5. 断续快照不能精确恢复每回合受伤速度；缺失观察不能解释为没有压力。

这些不确定性影响选址评分和实验结论，不影响合法动作的硬性校验。

## 4. 设计与模块接口

建议新增两个职责明确的小模块；不要增加通用插件系统或大规模改目录：

- `solution/layout.py`：方向、候选布局、射击覆盖和拓扑检查，只产出计划，不发动作。
- `solution/maintenance.py`：墙体建设/维护候选、预算和目标选择，通过现有调度层执行。

建议数据契约如下，名称可调整，但职责和字段语义不得缺失：

```python
@dataclass(frozen=True)
class WeaponPlacement:
    role_type: str
    pos: Pos
    controller_cells: tuple[Pos, ...]

@dataclass(frozen=True)
class DefenseLayout:
    front: tuple[int, int]  # 原始坐标中的四/八方向单位向量
    source: str            # user_prior / observed / legacy
    weapons: tuple[WeaponPlacement, ...]
    front_walls: tuple[Pos, ...]  # 完整分类，包含已建和计划墙
    flank_walls: tuple[Pos, ...]
    gates: tuple[Pos, ...]
    reason: str            # 简短稳定原因码，不包含输入原文
    wall_order: tuple[Pos, ...]  # 独立施工顺序，可交错正面和前侧翼

@dataclass(frozen=True)
class WallWork:
    kind: str              # build / repair / upgrade
    target: Pos
    target_id: int | None
    item: str | None
    urgency: int
    expected_hp_gain: int
    gold_cost: int
    reason: str
```

职责接口：

- `observe_defense(turn, state, config)`：每个新回合更新观察，不生成动作。
- `plan_layout(turn, defense_state, config, deadline) -> DefenseLayout | None`：返回完整可用方案；超时返回上一份仍有效方案或 `None`。
- `rank_wall_work(ctx, layout) -> tuple[WallWork, ...]`：给出有界候选，不改变预算、背包、动作和占位。
- `try_wall_work(ctx, role, work, max_trip) -> bool`：重新校验后执行一个合法动作或一步移动；成功后才登记预留。

`DefenseLayout` 必须由建塔、建墙、回防和维护共用，禁止各模块自行重新计算不一致的“前方”。`WallWork` 是内部计划，不新增任何 HTTP 字段或动作名。

避免循环导入：`layout.py` 的底层计算只依赖模型、几何、配置及简单状态结构；不要形成 `defense -> layout -> combat -> defense`。如需复用遮挡计算，抽出小型纯几何函数并由布局与攻击共同使用，保持现有伤害语义和测试。

## 5. 来敌方向和跨回合观察

### 5.1 初始方向

- `front_direction=east/west` 是显式覆盖，便于受控实验。
- `auto` 时根据基地实际占地相对地图水平中线的位置推导：左半边朝东，右半边朝西。不用角色 ID，也不把某个 teamType 永远等同于左侧。
- 屏幕方位与原始坐标必须通过已知地图样本确认；本方案中的 east 指原始 x 增大方向。无需依赖 y 的正向来推断上下。
- 基地接近中线、地图缺失、占地异常等无法判断的情况，退回原布局，记录原因。
- 几何排序的并列情况用已有归一化坐标打破，保证镜像可复现。

### 5.2 用观察修正压力，而不是反复重建

首个有可靠机器人观察的夜间快照记录来敌方向，之后持续统计各侧压力：

- 优先考虑明确以我方为目标的机器人；目标未知但已逼近我方也算威胁。
- 不把远处明确针对对方的机器人用于确定我方主来路；近处真实危险仍计入。
- 以相对基地位置归入八个方向，按攻击力、距离和接近趋势加权；限制采样数量。
- 同时记录正面敌群数量、横向分布宽度，以及向前排两端外侧接近的机器人。数量增加只是分流风险提示；已有前侧翼机器人或墙体受损是更直接的补墙依据。区分单侧与双侧压力，不能把正常分流误判为主来敌方向改变。
- 需要连续有效观察支持方向变化，不能一只绕行机器人就翻转全局布局。
- 第一座武器落成后冻结本局的武器布局方向。之后压力变化只调整未建墙的顺序、维护优先级和操控位置；不自动搬塔。
- 记录 user_prior 和 observed 的差异，供下一局配置修正，不把“首夜看到的位置”强称为真实出生坐标。

### 5.3 受损记录

按单位 ID、位置和类型记录上一次血量、等级、观察回合及每侧累计受损：

- 只在相邻、有效快照且等级相同、身份和位置相同的条件下，用 `max(0, old_hp-new_hp)` 计入受损。
- 升级、修复、重建、ID 复用、回合跳跃时另作标记，不能把净变化当完整伤害记录。
- 缺失单位标为 unavailable；明确 health<=0 才记死亡。无法确认破坏时不伪造损失量。
- 回合重复不累计；新对局和地图/基地签名变化清空相关缓存。复用已有 generation 重置机制。
- 仅保存最近配置窗口的聚合和少量快照；不要持久化原始请求或添加无界事件列表。

## 6. 联合布局算法

### 6.1 候选空间与顺序

1. 基于完整基地 footprint 枚举蓝圈、黄圈内且在地图中的格子。
2. 投影到“前向轴”和“横向轴”，区分正面、侧翼和后方。以整个 footprint 的前边界判断正面，不仅用基地锚点。
3. 固定已有存活建筑；从有限的合法武器位、操控位和出入口中生成候选方案。
4. 先枚举火箭后方位，再考虑电磁炮的侧后方射击通道；比较组合，不使用三次独立贪心占位。
5. 对每个候选完整布局进行硬约束过滤，再按覆盖、角色风险、前线阻挡代理指标和建造成本排序。
6. 首日选定方案后保存；每回合验证其剩余部分，失效时局部重规划。不可为了小幅评分变化来回跑向不同建设点。

不能假设用户地图总是足够宽或基地后方有三个空位。没有可用后方位置时，优先扩大到侧方，再回退现有安全策略，而不是输出非法位置或无火力方案。

### 6.2 硬约束

- 建筑格合法且不重叠，不占中立区、现有建筑、角色或已预留的目的格。
- 当前角色占着未来建设点时允许等待或换步骤，不立刻抛弃整个长期布局。
- 每座计划武器至少有一个合法相邻操控格；三座武器存在三个不同操控格的联合分配。
- 工人能到达待建位置的相邻格；施工顺序不会封死下一步施工、维修或回防路线。
- 当前角色和计划操控格都能连通到安全的侧后方出口。检查整套拟建布局及每一步累积预留，不仅检查单面墙。
- 遵守八方向和对角穿行。验证“形成连续阻挡”时同样允许机器人走对角，不能用四邻接图制造虚假的封锁。
- 其他塔不能让实际需要的射击方向全部被遮挡；基地和墙不参与弹道遮挡判断。射程只按运行时值或有来源的初建等级参数计算。
- 夜晚不建墙、不建塔。建筑遮挡不能用于缩小既有角色危险区域。

### 6.3 火力覆盖的可执行检查

不能仅朝地图中心打一条射线。至少选取正面中央、两个侧翼和靠近前排墙外的若干代表来敌点，数量有上限；这些点是测试布局的假设位置，不是假装观测到的机器人。

对每个武器候选：

- 检查其初建等级的射程和弹道，不能拿未来三级属性证明首夜安全。
- 火箭可跨越建筑，但冷却空窗不能按持续输出计算。
- 电磁炮/加特林按当前遮挡配置检查其他塔；尚未建成的计划塔也需检查。基地、已有墙与计划墙均不参与弹道遮挡。
- 先过滤“正面中央完全打不到”的组合，再比较多个方向的有效覆盖；不得将一发零星侧向火力称为足够防守。
- 保留短射程加特林对照组合测试：如果后撤失去核心覆盖，就选更靠侧前但仍受保护的位置，或明确回退。

墙和基地不阻挡武器弹道，因此不再为了弹道在正面墙上留缺口，也不因基地在射线上否决后方塔位。出入口仍按角色通行需要保留；其他塔造成的遮挡仍需评估，不能据此关闭所有建筑遮挡。

### 6.4 墙的分段建设

- 首批三座武器仍优先落成，避免为造墙耽误首夜基本火力。
- 第一段选择直接覆盖基地正面投影及主要进入通道的墙。默认目标 4 格是实验参数，不是必须填满的硬指标。
- 将前排两端附近、黄圈侧边靠前的连续格子作为“前侧翼”候选，按投影与拓扑识别，不写死某张地图坐标。它们用于应对敌群拥挤后的横向分流，与靠后的侧墙区别排序。
- 前侧翼补墙不是必须等正面目标数量建满才执行。若某侧已有接近敌人、上一夜受损，或正面敌群密集且横向分布扩大，可以先补该侧关键格，再继续正面剩余墙位。两侧都有压力时按风险分别安排，不能只保护固定一侧。
- 敌人较少、来路集中时不因数量阈值机械扩墙；达到关键防御需求后停止。夜间只更新压力和次日施工优先级，不发建造动作。后墙默认不主动铺满。
- 每加一格都重做连通性检查；武器布局变化时重做射击覆盖检查。无法建满目标数量时接受较少但有效的墙，不能无限寻路或不断购买石头。
- 评估墙是否落在接近基地的主要通道上，以及加入该墙后绕行距离/可通行入口如何变化。这只是路径代理指标，不声称复现机器人 AI。
- `max_walls` 是上限，不能继续作为“必须建满”的任务目标。达到有效前线目标且压力低时停止建设，恢复经济和任务。

## 7. 墙体维护与资源分配

### 7.1 统一维护目标

对前排与侧翼墙分别评估：剩余血量、近夜受损、当前附近压力、缺口后果、维护路线和动作机会成本。承受分流敌群攻击的前侧翼墙按实际风险参与同一排序，可以优先于压力较低的正面墙，不能仅因属于“侧翼”而被固定降级。

使用可解释的顺序：

1. 正在承担攻击、预计近期失守的关键墙。
2. 上一夜承受大量攻击、需要为下一夜恢复的关键墙。
3. 有明确后续压力依据的正面加固。
4. 低压力侧后方墙默认不主动升级，避免只因血少就获得预算。

压力估计不得依赖猜测的精确仇恨。相邻有效回合受损均值可作短期受损速度；附近机器人攻击力只能作风险上界或排序指标，不能声称这些机器人一定攻击该墙。证据不足时标记 unknown，使用保守排序。

### 7.2 比较修复、升级与补墙

对同一现存墙，分别产生合法修复/升级候选：

- 修复增加血量：`max(0, current_max_hp-current_hp)`。
- 升级增加血量：`max(0, next_level_max_hp-current_hp)`，包含恢复和血上限增加。
- 可估计额外支撑回合：`hp_gain / recent_damage_per_round`；分母未知或为零时不输出无穷收益，不以该项单独购买。
- 同等紧迫程度下比较恢复收益、预期多争取的回合、金币和取货/交付所需行动。
- 石头虽没有直接金币建造费，仍有采集、行走、售卖和角色占用成本；补墙不能算免费。
- 已有道具优先检查适用目标，但使用也消耗行动，不能只为清背包就浪费在满血或无压力墙上。
- 不自动拆墙重建回血，不覆盖升级建筑；这些改变需单独任务。

运行时若提供最大血量则使用它；模型尚未支持时做向后兼容解析。否则用集中、有来源的等级表，并在诊断标注 estimated；不要把“本局观察到的最高血量”当成真实最大血量。当前已读规则的墙等级血量可集中为 1000/1500/2000，运行时明确值优先；未知等级不猜测。

满血墙只有存在下一夜压力依据且预算允许才考虑预防升级。不要机械规定残血才升级，也不要每次受一点伤就修满。

### 7.3 预算和任务去重

- 先保留未建武器成本以及已决定的基地应急、角色治疗开销。
- 每日记录起始金币、已确认收入、已确认支出及预留；墙道具累计购买上限为 `floor(wall_budget_fraction * 可分配资金基数)`，默认比例 0.25。资金基数为当日起始金币加已确认收入，再扣当日已花和仍需预留的基本武器、基地/角色应急费用，最低为零。后续收入可增加额度，避免首日建塔后额度为零就整天无法维护；同一笔收入不能重复计入。
- 每次购买还需同时满足实时余额扣除全部预留后的限制，不能只看累计额度。卖矿收入结合成功动作和背包变化确认；无法归因的金币变化不得直接当作新增收入。缺失中间回合时采用保守额度，不猜测未观察交易。
- 维护购买使用实时商店价格；商品缺失、数量/价格无效或背包装不下就跳过。
- 已成功购买的开销和当回合已预留购买都计入额度；请求失败释放预留，未知结果等待背包/金币变化确认，不重复计费。
- 道具购买以明确的目标墙为依据。队伍已有匹配券、正在取货、正在交付时不得重复购买。
- 保存小型待交付任务：角色、目标、物品、阶段、创建回合和失效条件。墙死亡/不可见、等级不符、路径失效、角色死亡或超时后重新评估。
- 各角色共享金币和目标预留；只有 `ctx.add()` / `ctx.move()` 成功才更新任务阶段。预留与已确认消耗必须分开。
- 已持有的券使用不重复扣本日购买额度；放弃交付任务也不代表已买道具的支出消失。
- 当额度低于最便宜有效方案时停止购买，不能挪用武器重建或基地应急预算来追求墙数量。

### 7.4 调度位置，防止建设饿死维护

当前 `build()` 在 `supplies()` 前，工人可能一直补墙而没有机会维修。新模式要显式区分武器建设、前线缺口、关键墙维护和普通补墙。

白天建议顺序：基地/角色应急 → 补齐基本武器 → 紧急前线缺口或关键墙维护 → 第一段前墙 → 其他经济与任务。普通扩墙不能无限压住升级/修复；先驱者任务优先级保持不变，不默认抽走先驱者长期搬运墙券。

夜间第一版采用保守边界：

- 先完成有效火力和操控者分配；不能用维护动作抢占已提交攻击的操控者。
- 只有通过现有释放条件的空闲角色，才可进行安全可达的维护、取货或交付。
- 不修改 `can_release()` 的证据要求；维护失败或攻击被丢弃后仍须保持现有二次清场检查。
- 没有空闲角色时保留维护任务，白天继续。为抢修主动牺牲某座塔火力属于后续实验，不在本次默认实现中。

## 8. 配置契约与兼容性

新增参数放在 `StrategyConfig`，校验放在 `configuration.py`。以下数值是初始实验值，测试支持且可调整，不声称已经最优：

| 字段 | 类型 / 范围 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `defense_layout` | legacy / frontline | legacy | 旧配置保持原行为 |
| `front_direction` | auto / east / west | auto | 人工方向覆盖用于实验 |
| `front_wall_target_count` | int，0～10，且不超过 max_walls | 4 | 正面建设目标上限 |
| `wall_maintenance_enabled` | bool | false | 新配置开启 |
| `wall_budget_fraction` | 有限 float/int，0～1，拒绝 bool | 0.25 | 当日墙道具预算比例 |
| `wall_emergency_horizon` | int，1～20 | 3 | 短期失守风险窗口 |
| `wall_observation_history_rounds` | int，1～260 | 130 | 受损观察窗口 |
| `front_observation_limit` | int，1～256 | 64 | 方向和压力取样上限 |
| `layout_candidate_limit` | int，1～512 | 128 | 候选布局硬上限 |
| `layout_search_budget_ms` | int，10～500 | 100 | 首次/失效重算的子预算 |

其他阈值如方向切换所需连续观察数、待交付超时，应集中定义并记录理由，不能散落魔数。

增加 `config/frontline.json`：与 baseline 相同武器组合和原有安全开关，仅开启 frontline 与墙维护及上述实验参数。增加 `config/frontline-balanced.json` 只用于新布局下三种武器对照。保留 baseline/balanced 文件行为，不能悄悄把默认模式换成 frontline。

参数校验必须覆盖枚举、布尔与整数区分、NaN/Infinity、范围、跨字段约束、未知字段和错误列表类型。`front_wall_target_count <= max_walls` 等新模式专属约束仅在 frontline 启用时检查；legacy 已有的 `max_walls=0` 配置不能因新字段默认值被拒绝。遇到无效配置应在启动时明确失败，不在比赛回合中才异常。关闭新模式后，不产生墙自动购买或新布局状态对旧策略的影响。

## 9. 性能、缓存和回退

- 共用现有 monotonic 总截止时间，不增加总回合预算；布局子截止取总截止与子预算的较早者。
- 仅对基地附近有限候选做拓扑/射线检查，不为每个候选跑全地图、多机器人完整模拟。
- 只在首次选址或结构性变化时重算布局；短暂角色占位不触发全量重算。资源区变化仅在影响出入口可达性时重验。
- 所有候选循环、BFS、压力采样均有数量/节点/时间限制。超时或遍历截断意味着“未证明可行”，不能当作安全通过。
- 未完成的候选不得写入缓存。优先复用上次仍合法方案，必要时采用 legacy 的逐动作安全检查；失败则不发该动作，继续其余策略。
- 建议本地验收目标：缓存命中布局部分 p95 < 5 ms；首建布局遵守配置的 100 ms 子预算，允许少量调度误差但不能拖到总截止。记录硬件、解释器和测量范围，不能把本机耗时当目标机保证。
- 不给所有回合添加大量日志，不向 HTTP 响应添加诊断字段；诊断输出需有数量与字节上限。

| 类别 | 输入与必须观察的结果 |

| 方向修正 | 首夜观察缺失、少量侧翼机器人、对方远处机器人、持续来路变化；布局不抖动、不自动拆塔 |
| 拥挤分流 | 正面密集敌群分别向单侧、双侧前侧翼接近；高风险前侧翼可在正面目标未建满时优先补齐，主布局方向不翻转；少量集中敌群不机械扩墙，夜间不建墙 |

| 维护选择 | 更低血的后墙与受压前墙并存时优先关键前墙；低压力不乱买；成本变化会改变修复/升级选择 |
| 恢复收益 | 残血升级包含恢复收益；满血无压力墙不修；最高等级无效券不使用；未知等级保守跳过 |
| 预算 | 当日额度、武器与应急预留、动态价格、商品缺失、背包满、两人同时购买均正确 |
| 闭环去重 | 已有券、购买在途、购买失败、移动失败、死亡、目标消失/升级、超时；不重复花钱或重复记账 |
| 回合状态 | 重复请求、跳回合、夜转日、升级回血、缺失单位、新对局；不虚增伤害或携带旧预算 |

## 12. 诊断与验收命令

在 `tools/diagnostics/` 新增 `defense_layout.py`，要求：

- 默认运行原创合成场景，可选 `--scenario left/right`、`--config`；原始坐标的 ASCII 布局与方向必须清楚。
- 输出武器、墙、操控格、出口、覆盖检查和回退原因的有界摘要；最多约 8 KiB，不输出原始平台数据。
- 可选本地 JSON 输入时要限制文件大小，不自动联网或执行任务命令。
- `--verify` 在硬约束不满足或发现非法动作时非零退出；legacy 和 frontline 分别使用各自应满足的条件。

以下接口已实现；运行路径均相对仓库根目录，验证结果见 `HANDOFF.md`：

```bash
make test PYTHON=python3.11
python3.11 -m unittest tests.test_layout tests.test_wall_maintenance -v
python3.11 tools/diagnostics/defense_layout.py --config config/frontline.json --scenario left --verify
python3.11 tools/diagnostics/defense_layout.py --config config/frontline.json --scenario right --verify
python3.11 tools/diagnostics/defense_layout.py --config config/frontline-balanced.json --scenario left --verify
python3.11 tools/diagnostics/defense_layout.py --config config/frontline-balanced.json --scenario right --verify
```

HTTP 验收，终端 A 启动服务，终端 B 发请求；检查完成后关闭自己启动的服务：

```bash
# 终端 A
PYTHON_BIN=python3.11 AGENT_CONFIG=config/frontline.json bash run.sh 8000

# 终端 B
python3.11 tools/diagnostics/smoke_http.py --port 8000 --scenario day
python3.11 tools/diagnostics/smoke_http.py --port 8000 --scenario night
```

分别替换配置再检查 legacy baseline 和 frontline-balanced；沿用异常 JSON、非对象输入的安全响应检查。现有 night 场景只能证明夜间有合法攻击，不能代替新建布局的多回合测试。

若已有合法脱敏 JSONL，请用现有工具：

```bash
python3.11 tools/diagnostics/replay.py local/turns.jsonl --config config/frontline.json --limit 100
```

`local/turns.jsonl` 是可选输入占位，不要求用户上传整份原始日志；不存在时跳过并如实说明，不创建伪平台数据冒充回放证据。

## 13. 平台验证与最终交付标准

本地可完成的验收：

- 原 99 项测试及新增场景通过；没有删除/弱化关键旧断言来制造通过。
- 所有配置可启动并通过相应 HTTP 检查；响应协议不变。
- 新布局在两侧均有可解释图示；不能成立的场景正确回退。
- 维护有真实的购买、交付、使用、失败恢复闭环，且有效火力未被误占。
- 统计新增代码的耗时上界与缓存行为；超时安全回退。
- 文档明确 legacy 是对照、新模式是候选，不能把未测假设写为确认规则。
- 检查 diff、文件清单与敏感内容；不带官方材料、原始日志、本地索引或凭据。

平台实验另需授权。在相同地图/随机种子可控时，进行两侧成对比较；不能控制随机性时说明混杂因素。至少覆盖早期与后期波次，先跑小样本查异常，再扩展，不以一局定论。

记录：基地存活/剩余血量、操控者死亡、墙体实际受损和被毁次数、建墙石头数、墙道具金币、维修占用行动、有效攻击回合、击杀和任务收益、异常数。把“有效攻击回合”与“发出攻击指令数”区分开；没有命中证据时只能报告后者。

最小机制实验：

1. 相同来路下对照有无一段正面墙，观察机器人路径、先攻击谁、是否绕过/越过墙攻击基地。
   在较密集波次中进一步对照“仅正面墙”与“正面墙加靠前侧翼墙”，记录敌群横向分流、两端绕行、侧翼承伤和额外资源开销；不能只看墙数量增加。
2. 电磁炮/加特林分别在无遮挡、墙处于弹道上、基地处于弹道上时攻击同位置机器人；墙和基地都应保持相同伤害；另设其他武器工事在弹道上的对照，验证其遮挡行为。
3. 前方与侧后方塔位对照，检查开始开火的时机、冷却空窗、操控者受击和基地承伤。
4. 受损关键墙的修复与升级对照，记录成本和实际多支撑的回合，不能只比较面板血量。

如果前墙不能吸收威胁，或后撤显著损失输出，就保留候选配置和实验结果，收缩到“按受损压力维护墙”的有效部分。不能为了满足布局图形而牺牲基地安全。

Grok 最终报告必须列出：改动文件、各配置行为、实际执行的验收命令与结果、未执行的目标环境/平台验证、已知回退条件及未解决问题。本文不要求也不允许凭合成测试宣称达到前三或提高胜率。
